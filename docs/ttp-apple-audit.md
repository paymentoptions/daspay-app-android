# DASPay — Apple "Tap to Pay on iPhone App Requirements" v1.7 Audit

**Scope:** `daspay-app-android` repo, KMP shared module (`commonMain`/`iosMain`), `iosApp` Swift glue, Xcode project settings, Info.plist, entitlements. PSP: MineSec (Headless SDK). Market: Singapore. Distribution: Unlisted App.

**Method:** static code review only (read-only). No device testing was performed. "Done" is only used where a concrete file:line shows the requirement is implemented *and* wired into a real code path (not dead/unused code).

**Headline finding (superseded by steps 3–4):** the original finding was that the app never called MineSec's `HeadlessService.linkAccount()`, leaving almost every requirement in the "Enabling Tap to Pay" and "Merchant Education" sections (3.1–4.7) with no code to evaluate. Steps 3–4 closed most of that: `linkAccount()` is now called from `EnableTapToPayFlow`, and `ProximityReaderDiscovery` covers the merchant-education content automatically. 3.1/3.2/3.3/3.9 remain open — see §2 item 14.

**Update (step 2):** the single-hardcoded-merchant-identity bootstrap described in the previous version of this finding (`businessName: "Pertok"`, `merchantId: "M1770891455"`, `merchantCategoryCode: "5999"`, `profileId: "prof_01M0Y76NPJ4EEKSS83M1NCHKG1"`, started unconditionally from `iOSApp.init()`) has been replaced: the SDK is now started exactly once, from the app-wide `ReaderLifecycleCoordinator` (shared Kotlin), with a per-session `MerchantConfig` built in `DPStorageManager.saveDeviceConfiguration()`. **However, the backend still doesn't return per-merchant values** — confirmed by reading `SignInResponse`/`SignInData` and `ExternalConfigurationResponse`/`DeviceInfo` in full: `merchantId` is populated from `DeviceInfo.MinesecMerchantId` and `terminalEmvProfileId` from `DeviceInfo.MinesecDeviceId` (the closest available fields), but `profileId`, `merchantBusinessName`, and `merchantCategoryCode` have no backend source at all today and are saved as empty strings pending a real endpoint. **Consequence: with an empty `profileId`, `initSoftPOS` will not succeed against the live MineSec backend** until that field is supplied — this is a known, explicitly-accepted gap, not an oversight, and should be the next thing closed once the backend exposes these fields.

**Android note (step 2):** decompiling the linked `headless-1.2.17-live-release.aar` confirms Android's MineSec SDK (`com.theminesec.sdk:headless`) has no app-visible reader-lifecycle, merchant-identity, or account-link API at all — `HeadlessSetup.initSoftPos(context, licenseFile)` takes no merchant config, and there is no `linkAccount`/`warmUp`/`accountStatus`/`readiness`/`getReaderStatus` method anywhere in the AAR (only private internals inside `HeadlessActivity`). Android's `TapToPayReader` implementation (`shared/src/androidMain/.../payment/reader/TapToPayReader.android.kt`) is therefore a thin wrapper over the existing NFC-adapter check — there is nothing to start/stop/warm up on this platform, by design of the SDK, not as a gap in this app's code.

**Update (step 6 — placeholders):** built the visual/copy scaffolding that was previously entirely missing for 3.1/3.2/3.9/5.5/6.2 and the sign-in "how to get an account" gap, using neutral placeholders so the final Apple hero asset / icon / copy can be swapped in later without touching code structure. Specifically: a full-screen Tap to Pay awareness splash (`TapToPayAwarenessScreen`) and a post-setup "try it out" screen (`TryTapToPayScreen`) now exist and are reachable via `Screens.TapToPayAwareness`/`Screens.TryTapToPay`, but — per this step's explicit instruction not to change any flow logic — neither is wired into an automatic trigger point yet (no auto-show on login/dashboard, no auto-navigate from `EnableTapToPayFlow`'s `onLinked` hook); that remains a future step. The iPhone-silhouette `tap_to_pay.png`/`payment_taptopay.png` bitmaps flagged under 5.5/6.2 as a likely branding violation have been deleted outright and replaced by one new neutral vector, `ttp_placeholder.xml`, used everywhere those bitmaps were (plus the iOS checkout button icon now uses the real SF Symbol `wave.3.right.circle.fill` via native UIKit interop, as specified). The sign-in screen now tells a new user how to get an account, linking to the real Payment Options Gateway onboarding/KYC flow. See the new "Step 6 placeholders" list at the end of this document for every `TODO(design)` left in the code.
